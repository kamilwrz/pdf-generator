## Pre-review audit — what already exists (0B)

   owner's monetization question." **Accepted fix:** minimal single-column
   waitlist table instead of `mailto:` — see updated item 2 below.
3. **Complexity was inverted relative to the actual ask** — items 1-4 map
   directly to the owner's stated ask and are cheap; items 5-8 (the
   owner-opted cherry-picks) generated most of the 11-section review's
   findings and add real engineering mass, all bundled as one diff with no
   checkpoint to learn whether the cherry-picks were worth it before building
   them. **Accepted fix:** split into two phases — see "Phasing" below.
4. **No cap on AI call volume, only a cache** — item 7 explicitly wants to
   *increase* AI Assistant call volume (success metric #1), while "unmetered
   spend is a hard constraint pre-M2" was mitigated only by content-hash
   caching, which stops redundant calls but not growth. **Accepted fix:**
   add a simple per-user/day call cap as a stopgap — see updated item 7.

**Noted but not converted into a separate scope decision** (folded into
existing sections/notes instead, since each has one obvious response, not a
real alternative to weigh):
5. Hiding deck/article behind a UI flag doesn't shrink actual maintenance/test
   surface — those codepaths can silently rot while hidden. Noted in NOT-in-

6. Item 5's industry tagging (assigning real industries to 8 templates that

7. The M0 drift pattern has now been named three times (2026-07-19,

## Accepted Scope — PHASE 1, ship now (baseline, from Approach B)
1. Hide "Slajdy AI" / "Artykuł AI" Topbar buttons behind a single exported
   `FEATURES.decksArticles = false` constant (new `frontend/src/config/features.js`,
   a build-time frontend constant — not a per-user DB toggle, not an env var; flip
   one line and redeploy to revert). `AiDeckPanel`/`AiArticlePanel` components,
   `deck_generator.py`/`article_generator.py`, and the 3 deck + 1 article templates
   stay in the codebase untouched. **Edge case:** any user with previously-generated
   decks/articles keeps them — `ModalPdfs.jsx` ("Moje dokumenty") is format-agnostic
   and stays unaffected by this flag, so existing deck/article PDFs remain visible,
   openable, and exportable there; only the *creation* entry points are hidden.
2. **[Revised per Outside Voice]** Fix the dead "Cennik" nav/footer link
   (`Hero.jsx:25,253`) and the hardcoded, logic-less "Plan darmowy" string
   (`Sidebar.jsx:80`) together — both are fake-monetization UI with no backing
   state. "Cennik" points to a new **inline section on the Hero page** (not a
   modal) titled "coming soon" with a single email field. **Capture mechanism
   (revised): a minimal waitlist table**, not `mailto:` — one new table
   (`email`, `created_at`), one unauthenticated `POST` endpoint, no new user
   model coupling. Rationale for the reversal: `mailto:` is this plan's only
   monetization-facing deliverable and produces no send confirmation, no
   count, and nothing queryable — it silently does nothing on machines without
   a configured mail client. A one-table waitlist is not meaningfully worse on
   GDPR exposure (an email lands somewhere the owner controls either way) and
   is the difference between "answered the owner's monetization question" and
   "looked like an answer." Basic validation (valid email format, simple rate
   limit on the endpoint to prevent spam-fill) is included in scope — this is
   now a real, if minimal, backend surface, not a zero-backend pass. The
   `Sidebar.jsx:80` "Plan darmowy" label is **removed entirely** (not replaced
   with different fake copy) until M2 introduces a real plan/credits field on
   `User` — an empty state is honest; a different hardcoded string is not.
3. Resolve the "CV AI" vs. AiAssistant naming collision: rename the Topbar
   "CV AI" button to **"Wypełnij z PDF"** ("Fill from PDF" — pinned copy, not a
   placeholder), and give the AiAssistant FAB a persistent visible label reading
   **"Asystent AI"** next to its icon (not icon-only), so the real analyzer/
   corrector — the feature that most directly matches the owner's new positioning —
   is discoverable.
4. Template-first onboarding: auto-open `TemplatesModal` when a user has never
   saved a PDF. **Verified during this review:** no loading/ready flag exists
   anywhere today — `PDFs` (`PdfCanvas.jsx:55`, plain `useState([])`) is only
   populated by a `useEffect` inside the always-mounted `ModalPdfs.jsx:153-161`,
   which fetches on mount, so `PDFs.length === 0` is genuinely ambiguous between
   "no saved PDFs" and "fetch still in flight" for a real, brief window on every
   `/pdfcanvas` load. This item must **add** a small `pdfsLoaded` boolean (set
   `true` once that existing fetch's `.then()` resolves, lifted into
   `PdfContext` alongside `PDFs`/`setPDFs`) — not "gate on an existing flag," as
   originally miswritten; there isn't one yet. Gate the auto-open on
   `pdfsLoaded && PDFs.length === 0`. If the user dismisses the modal without
   picking a template, set a session-scoped flag (`sessionStorage`) so it does
   not re-open again for the rest of that session — it will re-offer on their
   next fresh login if `PDFs.length` is still 0.

## Accepted Cherry-Picks — PHASE 2, gated on Phase 1 data (owner opted in, individually)
5. **Industry-based template recommendation** at the picker. **Verified during
   this review:** the `industry` field (`templates/index.js:29-48`) is a
   compound `"Group · Descriptor"` string, and the first segment is a real
   industry for only 8 of the 16 CV templates (`"Finanse"` ×4, `"IT"` ×4) — the
   other 8 use a style/layout bucket with no industry meaning (`"Classic"` ×4,
   `"Sidebar"` ×4). A chip-selector built naively off this field would surface
   nonsense chips like "Classic" next to "Finanse." This item therefore
   **includes** a small authoring pass: add a separate, clean tag per CV
   template — reuse `"Finanse"`/`"IT"` where accurate, and add 2-3 more real
   categories (e.g. `"Prawo"`, `"Marketing"`, `"Ogólne"`) so all 16 templates
   resolve to an actual industry, not the existing display-only `industry`
   string. **[Outside Voice addition]** This tagging is an editorial/content
   judgment (is a "Sidebar" template "Ogólne" or "Marketing"?), not a purely
   mechanical dev task — the 16 proposed tags must get explicit owner sign-off
   before shipping, not be silently decided by whoever implements this.
   Single-select chip-selector **inside the TemplatesModal itself** (not a new
   signup-time question). Pinned behavior: **sort matching templates to the
   top of the grid; no separate "Recommended" badge** — one mechanism, not
   two — and do not hide non-matching templates.
6. **Non-blocking template-switch confirmation.** Replace the native
   `window.confirm()` blocking dialog (triggered on template switch over
   non-empty canvas) with a toast + undo pattern. **Verified during this
   review:** the existing undo/redo stack in `useA4Elements.js` explicitly calls
   `resetHistory()` on template load "so you can't undo BACK into the previous
   document" (`useA4Elements.js:185-191`) — by design, template switches are a
   history-severing boundary for the *normal* undo/redo stack, so this feature
   must **not** reuse that rolling stack. **Also verified (correcting an error
   from this plan's own prior draft):** `buildSnapshot`/`applySnapshot`
   (`useA4Elements.js:152,194`) are private closures — the hook's actual return
   object (`useA4Elements.js:1532` onward) does not export either. They are
   NOT "already-exported." Pinned mechanism: this item **includes**, as an
   explicit prerequisite sub-task, adding these two functions to
   `useA4Elements()`'s return object. **11-section review addition (Section
   10):** since this turns two internal closures into public API, export them
   under intention-revealing names rather than their internal ones —
   **`captureCheckpoint`** (was `buildSnapshot`) / **`restoreCheckpoint`**
   (was `applySnapshot`) — zero extra cost since the hook is already being
   touched for this item. Once exported: capture one single-shot checkpoint via
   `captureCheckpoint()` immediately before the switch, held in a ref scoped to
   the toast only; "Undo" (within a 6-second window before the toast
   auto-dismisses) calls `restoreCheckpoint()` with it, **then clears the ref**
   so a stray second click on "Undo" is a no-op instead of re-applying
   (Section 4 finding); the normal `resetHistory()` call for the new template
   still proceeds unchanged after either outcome. No interaction with
   autosave beyond normal behavior — whichever state is current after the toast
   resolves is what the next 2s autosave tick persists, same as any other edit.
7. **Proactive AI score surfacing.** Auto-run a quick analyzer score
   (`ai_assistant_service.py`, already exists) and show it as a small badge —
   pinned trigger: fire on explicit save/export actions ("Utwórz PDF" /
   "Aktualizuj"), **not** on the silent 2s autosave tick. Pinned cache rule:
   reuse the last score keyed on a hash of the canvas's serialized text content
   (element `content` fields only, not position/style) — only re-run the AI call
   when that hash changes. Cache lives in component-local state scoped to the
   current editing session (not persisted across page refresh, not lifted into
   `PdfContext`) — a refresh simply re-runs the AI call once on next save, which
   is an acceptable cost given the trigger is already debounced to explicit
   save/export actions. This guards against unmetered OpenAI spend before
   credits/quotas exist (M2). Also show the score again at export time, next to
   the download, so the analyzer's value is visible at the payoff moment. (Two
   testable deliverables under this one item: the save-time badge, and the
   export-time display — both share the same cached-score logic.)
   **11-section review additions:** the badge gets its **own independent
   loading spinner**, decoupled from the save/export indicator (save/export is
   fast and local; the AI call is slower and must never make export feel
   stuck — this is the same rule as the "never blocks export" trigger design).
   Guard against a stale-response race: if a second save fires before the
   first AI call resolves, ignore the first response if its content-hash no
   longer matches current canvas state when it arrives.
   **[Outside Voice addition]** The hash-based cache stops *redundant* calls
   on unchanged content but does nothing to bound *growth* in unique calls —
   and this item's own success metric (AiAssistant open rate) explicitly
   wants to increase call volume, directly in tension with "unmetered spend
   is a hard constraint pre-M2." **Accepted fix:** add a simple per-user daily
   call cap (a hardcoded constant, e.g. 20/day — not a real quota/credits
   system, just a stopgap) on the proactive-trigger path specifically (does
   not affect manually-triggered AiAssistant actions via the FAB, which stay
   uncapped as they are today — only the new automatic trigger gets a cap,
   since that's the new *growth* surface this item introduces). Trivial to
   remove once M2 ships real metering.

## Backend fix — PHASE 1, ship now, independent of item 7's phase
(added during 11-section review, Section 2/3; kept in Phase 1 despite
originating from item 7's increased call frequency, because it's a real,
cheap, pre-existing production bug worth fixing regardless of when/if item 7

8. **Fix the exception-leak gap in the AI Assistant route**, surfaced because
   item 7 increases this route's call frequency from occasional manual clicks
   to every save/export. `ai_assistant.py:57-58` currently does
   `except Exception as exc: raise HTTPException(500, detail=f"Błąd asystenta
   AI: {exc}")` — a catch-all that leaks the raw exception string to the
   client. `_gpt()` in `ai_assistant_service.py:132-151` has no handling for
   OpenAI timeout, rate-limit, or malformed-JSON responses (only empty-content
   is explicitly handled, via a clear `ValueError`) — all of those fall
   through to the leaking catch-all today. Fix: catch OpenAI-specific
   exceptions (timeout, rate limit, `JSONDecodeError`) distinctly in
   `_gpt()`/`analyze_action()`, log full context server-side (action, a
   truncated element count — not raw CV content — and the exception type), and
   have the route return a generic, non-leaking message
   ("Asystent AI jest chwilowo niedostępny, spróbuj ponownie.") on any
   unexpected failure. Owner-approved scope addition — small (S effort),
   directly caused-worse by this plan's own item 7, not a drive-by refactor.

**Bug A — impure React state updater.** The first version of fix #2 put
side effects (`logEvent()` network call, `markTemplatesModalSeen()`

`setIsTemplates(bool => {...})`. `frontend/src/main.jsx:7` wraps the app in
`<React.StrictMode>`, which intentionally double-invokes functional state
updaters in development specifically to catch this class of bug. Reproduced

`handleShowTemplates` reads it.
